## Worktree Workflow

Each worktree derives a human-readable `WORKTREE_LABEL` from its directory name
and a hash-based `WORKTREE_ID` from the worktree root path, prefixed with `w`
so generated Android application ID suffixes remain valid. Override
`WORKTREE_ID` when you want a shorter or stable value across renamed folders:

```bash
WORKTREE_ID=feature-a make worktree-info
WORKTREE_ID=feature-a make build
WORKTREE_ID=feature-a make install-debug
WORKTREE_ID=feature-a make clean-worktree
```

`make worktree-info` prints the isolated Gradle user home, project cache,
`local.properties`, and debug application ID. Debug builds receive
`DEBUG_APPLICATION_ID_SUFFIX` through Gradle, so parallel worktrees can install
side by side on the same emulator or device. Set `DEBUG_APPLICATION_ID_SUFFIX=.debug`
to keep the classic single debug package name.

If the team later upgrades Gradle and needs to refresh the wrapper files, run:

```bash
make wrapper
```

Then regenerate `gradle/verification-metadata.xml` with Gradle's dependency-verification workflow, review every new checksum, and commit the updated wrapper and verification files together. The template pins the Gradle distribution SHA-256 and the official wrapper JAR SHA-256; `make verify-supply-chain` rejects a changed URL, checksum, dynamic version, or incomplete dependency metadata.

`make doctor` validates the active JDK, Android SDK root, `cmdline-tools/latest`, `adb`, emulator/AVD visibility, and the committed Gradle supply-chain controls before you spend time on builds.

## Release Setup

The generated starter treats build types like this:

- `debug`: default local development build, with a `.debug` application ID suffix and `-debug` version suffix
- `release`: production-shaped build intended for CI, beta handoff, or store preparation

Release signing is optional for local generation and verification. If signing inputs are missing, `assembleRelease` still gives you an unsigned release artifact that is useful for smoke validation. Store delivery uses a signed Android App Bundle (AAB) built by `bundleRelease`.

To wire real signing, choose one of these paths:

1. Copy the keys from `docs/release-signing.properties.example` into `local.properties`
2. Export `BIUCING_RELEASE_STORE_FILE`, `BIUCING_RELEASE_STORE_PASSWORD`, `BIUCING_RELEASE_KEY_ALIAS`, and `BIUCING_RELEASE_KEY_PASSWORD` in CI or your shell

The Gradle template also accepts the same values as Gradle properties:

- `biucing.release.storeFile`
- `biucing.release.storePassword`
- `biucing.release.keyAlias`
- `biucing.release.keyPassword`

For direct Gradle invocations, put these values in the user-level `~/.gradle/gradle.properties`, not the tracked project-level `gradle.properties`. The fastlane delivery lanes use `local.properties` or `BIUCING_RELEASE_*` so `make release-doctor`, `make archive`, `make beta`, and `make release` can verify the signing material before building.

Before a real Google Play handoff, the team also needs to supply:

- a Google Play Console app record for `{{APPLICATION_ID}}`
- a Google Cloud service-account JSON key that is invited to the Play Console app
- an upload keystore and all four signing values above

Copy `fastlane/.env.example` to `fastlane/.env`, place the service-account JSON under the ignored `credentials/` directory and the upload keystore under the ignored `signing/` directory, then replace the placeholders. See `docs/release-delivery.md` for the complete setup path.

`make verify` is the default local quality gate: it verifies the Gradle distribution, wrapper JAR, dependency checksums, then runs doctor, lint, unit tests, and a debug build. `gradle/verification-metadata.xml` enables strict checksum verification for downloaded plugins and dependencies.

`make verify-release-signing` opens the configured keystore and verifies that the configured alias is a usable private-key entry without printing any signing secret.

`make release-doctor` checks the service-account JSON path, release-signing inputs, upload keystore, private key, and enabled metadata configuration before a native bundle spends time building.

`make archive` runs lint, unit tests, signing-input verification, and `bundleRelease`, then cryptographically verifies every AAB JAR signature and compares its signer SHA-256 fingerprint with the configured upload-key certificate before printing the artifact checksum. A mismatch fails before any Play upload.

`make beta` runs the archive lane and uploads the AAB to the Google Play `internal` track by default.

`make release` runs the archive lane and uploads the AAB to the Google Play `production` track as a `draft` by default. It does not make the release public; complete the Play Console review and required compliance information before promoting the draft.

- `gradle/libs.versions.toml` is the source of truth for plugin and dependency versions.
- `.editorconfig` defines the baseline formatting behavior shared by Kotlin and Gradle Kotlin DSL files.
- `make doctor` is the fastest way to catch missing SDK, JDK, or emulator setup before `make build` and `make test`.
- `app/src/androidTest/` contains a starter Compose UI smoke test for the generated home screen.
- `core/network` centralizes starter environment metadata that multiple features can share.
- `core/testing` gives app and feature tests a shared fake environment provider.
- `core/designsystem` now holds starter color tokens, spacing tokens, dark theme colors, and reusable Compose UI primitives such as section cards and status badges.
- `app/` should stay focused on app shell concerns.
- `feature/home` and `feature/settings` demonstrate how the template can scale past a single screen.
- The starter design system is intentionally small, but it is structured so teams can grow tokens and reusable components without rewriting the first screens.
- Dark mode is part of the starter theme contract, so new components should prefer `MaterialTheme.colorScheme` and shared tokens over hard-coded colors.
- `gradle/wrapper/gradle-wrapper.jar` is committed in the starter and should stay versioned in the repo.
- `gradle/wrapper/gradle-wrapper.jar.sha256`, `distributionSha256Sum`, and `gradle/verification-metadata.xml` are reviewable supply-chain inputs; never regenerate or accept checksum changes blindly.
- `docs/release-signing.properties.example` documents the expected signing keys without committing secrets.
- `.gitignore` protects the recommended `credentials/` and `signing/` directories, keystores, local signing property files, and Fastlane credential JSON. It cannot protect files already tracked or force-added.
- `fastlane/Fastfile` owns Google Play credential checks, signed AAB creation, internal-track delivery, and draft production delivery.
- `scripts/verify-release-artifact` verifies AAB archive structure, its JAR signature, and the exact upload certificate; `scripts/artifact-info` records the verified artifact checksum.
- Google Play store listings can be managed from `fastlane/metadata/android` after `fastlane supply init`; Data safety, content ratings, policy declarations, and review answers remain Play Console responsibilities.

## Binary component architecture

The product build includes only `app/`. `components/` is an independent Gradle build
for `core/` and `feature/` sources. The shell consumes immutable Maven AARs, including
precompiled Dagger graphs, resources, Kotlin wrappers and the JNI library. Pure JVM
contracts may later be extracted as JARs; the starter currently publishes Android libraries as AARs.

Install `ndk;28.2.13676358` and `cmake;3.22.1` with your SDK manager before building
components. `ANDROID_HOME` must identify that SDK. The native SDK contains arm64-v8a
and x86_64 slices; other ABIs require an explicit build/publication contract change.

```sh
make components-bootstrap       # publish initial SDKs, lock and resolve, write Gradle locks
make components-info
make components-test
make core-test
./scripts/test-native            # host JVM/JNI tests; requires CMake and a JDK with JNI headers
./scripts/verify-di              # missing binding + cycle rejection in SDK and shell
```

Commit `dependencies/components.lock.json` and Gradle lockfiles after bootstrap.
The component lock fixes the complete SDK version combination and manifest hashes;
Gradle locks fix resolved third-party versions. Verification metadata checks external
artifacts; SDK artifacts are verified against the component lock on every Gradle invocation.
Missing locks fail explicitly and never switch the shell to source dependencies.

A component can be published independently:

```sh
python3 scripts/components publish home --version 0.1.1
# Explicitly update dependencies/components.json to the new version, then:
python3 scripts/components lock
python3 scripts/components resolve
./gradlew :app:dependencies --write-locks
make verify
```

Publications cannot overwrite existing versions. The default repository is
`.artifacts/maven`; `COMPONENT_REGISTRY` may point to a team-synchronized Maven directory.
Remote upload/authentication is not configured. Manifests record source hashes, tools,
SDK dependencies, resources and native ABI information. SharedCore publications retain
matching unstripped binaries in `symbols/<abi>/`; app release builds also produce R8 mappings.

Local iteration still consumes binaries. Publish the locked version to a separate
`COMPONENT_REGISTRY`, then explicitly select its version directory:

```sh
python3 scripts/components override set home /absolute/local/maven/group/path/home/0.1.0
python3 scripts/components override info
python3 scripts/components override clear home
```

Overrides must retain the locked coordinate and dependency versions. They are ignored
by Git and forbidden in CI and Release, including direct Gradle/Android Studio builds.
After changing a dependency contract, rebuild affected SDKs and validate the new complete combination.

`SessionOwner` owns a separate Dagger session graph and survives Activity recreation.
Its `onCleared` starts nonblocking native shutdown. `CoreSession.close()` waits for
accepted work to finish; coroutine cancellation forwards a native cancellation token
and does not imply that the native call has returned. No native handle is persisted
across process death. Core state is authoritative; UI holds presentation snapshots.

The portable C++ source is materialized from BiucingCLI's authoritative `shared/core/`
with `scripts/sync-shared-core`; repository tests reject drift between Apple and Android.
Generated products own their delivered copy. For later cross-repository development,
publish this core from a single versioned source repository instead of editing divergent copies.

Binary acceptance must include emulator/device JNI execution, resources, Activity
recreation and a minified release. `make test-ui` covers the first three; `./gradlew
assembleRelease` compiles the minified consumer. Host JNI tests do not replace Android execution.
