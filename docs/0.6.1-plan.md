# BiucingCLI 0.6.1 Plan

## Current State

BiucingCLI `0.6.0` made all seven starters worktree-ready:

- each template declares `worktree.support_level = worktree-ready`;
- generated projects expose `make worktree-info`, `make worktree-doctor`, and `make clean-worktree`;
- Docker-first templates isolate Compose project names, Docker volumes, image tags, host ports, dependency stores, and caches;
- native templates isolate the main build/cache/signing/app-identity collision points.

The remaining gap is polish under pressure.
The generated starters are safe to use from parallel worktrees, but they are not yet as consistent, self-diagnosing, or evidence-backed as they can be.

## 0.6.1 Theme

`0.6.1` should harden worktree isolation until it feels boring.

The release should not add new templates or a new orchestration layer.
It should make the existing worktree-first behavior more consistent, easier to reason about, and harder to misuse.

## Release Thesis

A generated starter should make worktree identity and collision risks obvious before the user starts a long-running workflow.

The same generated project should support:

- deterministic identity across all template families;
- readable diagnostics for humans and stable identifiers for tools;
- useful port-conflict advice before Docker services fail;
- stronger Docker doctor checks that validate Compose config without starting containers;
- native build evidence that distinguishes static, doctor, and real-build proof;
- conservative HarmonyOS identity behavior with a documented boundary.

The user-visible promise is:

> Parallel worktree development should be predictable by default, diagnosable when something is wrong, and backed by repeatable release evidence.

## Planning Principles

- keep `WORKTREE_ID` as a simple overridable Makefile variable;
- use one identity model across all seven templates;
- prefer explicit suggestions over hidden mutation;
- avoid auto-editing `.env`, Makefile, build profiles, or local signing files;
- keep diagnostics fast and safe to run before heavier builds;
- make release evidence say exactly what was checked and what was skipped.

## Hardening Targets

| Area | 0.6.0 status | 0.6.1 target |
| --- | --- | --- |
| Worktree identity | Docker-first templates use path hash; native templates mostly use directory slug | all templates use one identity model with `WORKTREE_LABEL`, `WORKTREE_ID`, and `WORKTREE_SLUG` |
| Port conflict handling | Docker templates warn when default ports are used | Docker templates detect occupied ports and print suggested overrides |
| Docker diagnostics | Compose config checks are documented in release evidence | generated projects expose a reusable doctor/config target for Compose rendering |
| Native evidence | native release evidence uses diagnostics and dry-run command expansion | verification docs separate static, doctor, and real-build evidence tiers |
| HarmonyOS debug identity | suffix is passed as a build property and source bundle name stays stable | document and, only if reliable, add opt-in temporary debug profile generation |
| Release evidence | 0.6.0 has a release-prep proof file | 0.6.1 release-prep captures the stronger hardening checks |

## Unified Worktree Identity

Every template should converge on this identity model:

```make
WORKTREE_ROOT ?= $(shell git rev-parse --show-toplevel 2>/dev/null || pwd)
WORKTREE_LABEL ?= $(shell basename "$(WORKTREE_ROOT)" | tr '[:upper:]' '[:lower:]' | tr -cs 'a-z0-9' '-' | sed 's/^-//; s/-$$//')
WORKTREE_ID ?= $(shell printf '%s' "$(WORKTREE_ROOT)" | shasum | cut -c1-8)
WORKTREE_SLUG ?= $(APP_NAME)-$(WORKTREE_ID)
```

Meaning:

- `WORKTREE_LABEL` is human-readable and derived from the worktree directory name;
- `WORKTREE_ID` is the short hash used as the isolation key;
- `WORKTREE_SLUG` combines the app/template runtime name with `WORKTREE_ID`;
- users can still override `WORKTREE_ID` when a team wants names like `main`, `alice-login`, or `release-check`.

## Workstreams

### Workstream 1: Contract Tightening

Make the 0.6.1 standard explicit before code changes.

Deliverables:

- add this plan;
- add a 0.6.1 task breakdown;
- update README and roadmap links;
- define what remains intentionally deferred.

### Workstream 2: Unified Identity

Make every template use the same `WORKTREE_ROOT`, `WORKTREE_LABEL`, `WORKTREE_ID`, and `WORKTREE_SLUG` model.

Deliverables:

- update Docker-first and native Makefiles;
- update generated README guidance where the old identity behavior is described;
- update unit tests and generated-project smoke evidence.

### Workstream 3: Port Conflict Advisor

Make Docker-first templates detect occupied host ports and print copy-pasteable overrides.

Deliverables:

- add a reusable shell snippet or Makefile pattern for port checks;
- cover `frontend`, `web-service`, and `microservice`;
- keep `worker` explicit about having no published host ports by default.

### Workstream 4: Stronger Docker Diagnostics

Make Compose config validation a generated-project command rather than only release evidence prose.

Deliverables:

- add a target such as `worktree-compose-config` where Compose is used;
- have `worktree-doctor` call or reference the config check;
- keep the check non-invasive and container-free.

### Workstream 5: Native Evidence Hardening

Make native release proof more precise.

Deliverables:

- update verification docs with `static`, `doctor`, and `real-build` evidence tiers;
- add 0.6.1 generated-project evidence commands;
- record environment-specific limitations without weakening the worktree claim.

### Workstream 6: HarmonyOS Debug Identity Boundary

Decide whether HarmonyOS should do more than pass a requested debug bundle suffix.

Deliverables:

- inspect the current template boundary;
- document whether temporary bundle rewriting is safe enough for 0.6.1;
- if safe, implement an opt-in target that writes only temporary ignored output;
- if not safe, record the decision as deferred.

### Workstream 7: Release Prep

Prepare 0.6.1 evidence and release docs.

Deliverables:

- add `docs/0.6.1-release-prep.md`;
- update README, roadmap, changelog draft, release checklist, and verification matrix;
- run repo-level checks and fresh generated-project worktree hardening evidence.

## Non-Goals

- automatically creating, deleting, or managing Git worktrees;
- adding a daemon, port registry, or background coordinator;
- auto-editing local files to resolve conflicts;
- guaranteeing conflict-free access to external shared services that the user manually points several worktrees at;
- forcing HarmonyOS bundle rewriting if the DevEco/hvigor toolchain boundary is unclear;
- requiring every maintainer machine to have every native SDK installed.

## Exit Criteria

`0.6.1` should be considered ready when:

- all templates use the same worktree identity model;
- Docker-first templates give actionable port conflict advice;
- Docker-first templates can render Compose config through a generated target;
- native release evidence clearly distinguishes static, doctor, and real-build proof;
- HarmonyOS debug identity behavior has an explicit supported/deferred decision;
- the release prep document records fresh generated-project evidence.

## Suggested Changelog Direction

If this scope lands, the `0.6.1` changelog should read as a worktree hardening release:

- unified worktree identity across all starters;
- added clearer Docker port and Compose diagnostics;
- strengthened native worktree verification evidence;
- clarified HarmonyOS debug identity support boundaries;
- expanded release evidence around collision detection and cleanup behavior.
