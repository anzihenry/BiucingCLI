# BiucingCLI 0.6.0 Plan

## Current State

BiucingCLI `0.5.0` has reached a mature template portfolio:

- seven starters are available:
  `frontend`, `web-service`, `microservice`, `worker`, `apple`, `android`, and `harmonyos`;
- the generator supports inspectable creation through dry-run, plan output, JSON metadata, and repo-level validation;
- Docker-first templates already route development, checks, and runtime packaging through Makefile and Compose workflows;
- native templates now include stronger doctor, release, signing, and generated-project validation guidance.

The next product gap is no longer raw template completeness.
The next gap is repeated use under real development pressure: multiple branches, multiple experiments, and multiple generated projects running side by side.

## 0.6.0 Theme

`0.6.0` should make BiucingCLI's starters worktree-first.

The release should make every generated project safe to use from multiple Git worktrees at the same time, without requiring the developer to manually rewrite ports, rename containers, clear caches, or protect local signing state by memory.

## Release Thesis

A generated starter should treat Git worktrees as a normal daily workflow.

The same repository should support:

- one worktree running a feature branch dev server;
- another worktree running tests;
- another worktree building a release artifact;
- another worktree experimenting with dependency upgrades;
- all of them using isolated local dependencies, caches, generated files, app identities, and runtime names.

The user-visible promise is:

> Every generated starter can be developed, tested, and packaged from parallel Git worktrees without accidental cross-worktree interference.

## Planning Principles

- prefer deterministic local isolation over hidden global state;
- keep generated projects simple to understand after generation;
- make default behavior safe, while keeping every derived value overridable;
- use Makefile and project-local scripts as the primary control surface;
- avoid adding a new runtime service or heavy orchestration layer;
- validate isolation with real generated projects wherever practical.

## Worktree Isolation Contract

Every template should document and, where applicable, implement these isolation dimensions.

| Dimension | Requirement |
| --- | --- |
| Worktree identity | generated projects expose a stable `WORKTREE_ID` and `WORKTREE_SLUG` derived from the current worktree path or an explicit override |
| Runtime names | containers, Compose projects, Docker volumes, runtime images, and local app identifiers do not collide across worktrees |
| Ports | host ports are overridable and documented; templates with long-running services provide a predictable way to avoid collisions |
| Dependency stores | local Postgres, Redis, OTel, and similar dependencies are isolated by Compose project, volume, and network |
| Caches | language/tool caches are either project-local or worktree-local when shared cache corruption or cross-branch state can hurt reliability |
| Generated output | build artifacts, generated code, package output, and IDE output do not require deleting another worktree's state |
| Local secrets | `local.properties`, signing material, `.env.local`, and similar files stay git-ignored and worktree-local |
| Installed app identity | native templates can install parallel debug builds by deriving bundle/application IDs when needed |
| Cleanup | each starter exposes a focused cleanup path for worktree-local runtime state |
| Diagnostics | each starter exposes a quick command that prints the resolved worktree identity and isolation values |

## Shared Generated Workflow

Every template should converge on these targets when they are meaningful for that platform:

```bash
make worktree-info
make worktree-doctor
make clean-worktree
```

`make worktree-info` should print the values that explain why this worktree is isolated:

- repo root;
- worktree root;
- `WORKTREE_ID`;
- `WORKTREE_SLUG`;
- Compose project name or native app identity suffix;
- important cache paths;
- important host ports;
- local-only config files.

`make worktree-doctor` should fail or warn when a worktree is likely to collide with another one:

- missing or duplicate host port overrides;
- global cache paths where local cache paths are expected;
- ignored local config files missing when a release flow needs them;
- native application IDs that would overwrite another installed debug build.

`make clean-worktree` should remove only state owned by the current worktree.
It must not delete shared Docker images, global SDKs, unrelated containers, unrelated Gradle caches, or files outside the generated project unless the user passes an explicit stronger target.

## Workstream 1: Contract and Generator Support

### Problem

The repo has strong template metadata, but it does not yet describe whether a template is safe for parallel worktree use.

### 0.6.0 Goal

Make worktree isolation a first-class template quality bar.

### Candidate Deliverables

- add a worktree isolation contract document;
- add metadata fields that describe a template's worktree support level;
- extend `biucing info` and JSON output to show worktree isolation status;
- extend `biucing validate` so every template declares its worktree contract;
- add tests that lock the new metadata and validation rules.

## Workstream 2: Docker-First Template Isolation

### Problem

The Docker-first templates are the highest-risk and highest-value targets for worktree isolation because they run long-lived services, publish ports, create Docker volumes, and often run in several branches at once.

### 0.6.0 Goal

Make `frontend`, `web-service`, `microservice`, and `worker` safe for parallel worktree development by default.

### Candidate Deliverables

- derive `COMPOSE_PROJECT_NAME` from `WORKTREE_SLUG`;
- make Docker volume names and image tags worktree-aware;
- make host ports explicit, overridable, and visible in `worktree-info`;
- keep Go, pnpm, Playwright, lint, and generated artifact caches project-local or worktree-local;
- update README and Makefile guidance for parallel worktree workflows;
- validate with at least two generated projects using different worktree identities.

## Workstream 3: Native Template Isolation

### Problem

Native templates do not mostly collide through containers; they collide through build caches, IDE state, simulator/device installs, signing files, and local SDK output.

### 0.6.0 Goal

Make `apple`, `android`, and `harmonyos` safe to build and test from parallel worktrees.

### Candidate Deliverables

- Apple:
  - isolate Xcode DerivedData;
  - isolate SwiftPM build output where practical;
  - support a debug bundle identifier suffix for parallel simulator installs;
  - print Tuist/Xcode output paths in `worktree-info`.
- Android:
  - isolate Gradle user home or project cache paths where useful;
  - support debug `applicationIdSuffix` derived from `WORKTREE_ID`;
  - keep signing and `local.properties` strictly worktree-local;
  - document emulator install behavior.
- HarmonyOS:
  - isolate `.hvigor`, `oh_modules`, and build output expectations;
  - support a debug bundle-name suffix if the toolchain supports it cleanly;
  - keep signing material local and visible in diagnostics without printing secret values.

## Workstream 4: Verification and Release Evidence

### Problem

Worktree safety is easy to claim and easy to regress.
The release needs a repeatable proof path that does not require every maintainer to remember the collision matrix.

### 0.6.0 Goal

Add a release verification path for worktree isolation.

### Candidate Deliverables

- add generated-project smoke checks for `worktree-info`;
- add tests that assert generated Makefiles include the required worktree targets;
- add docs for how to verify two generated projects side by side;
- update the verification matrix with worktree-specific release checks;
- prepare `0.6.0` release evidence around parallel-worktree behavior.

## Suggested Release Sequencing

### Phase A: Contract and Audit

- define the worktree isolation contract;
- audit all seven templates against the contract;
- classify gaps as blocking, important, or optional;
- decide which metadata fields should represent worktree support.

Status:
complete for planning.
See [Worktree Isolation Contract](worktree-isolation-contract.md) and
[0.6.0 Worktree Collision Audit](0.6.0-worktree-collision-audit.md).

### Phase B: Generator Metadata and Validation

- add worktree metadata to every `template.json`;
- expose it through `list`, `info`, and JSON surfaces;
- update `validate` to require declared worktree support;
- add golden and unit coverage.

Status:
complete for the generator contract surface.
All templates now declare worktree support in metadata, and
`biucing info`, JSON output, and `biucing validate` enforce the shape.

### Phase C: Docker-First Template Implementation

- update `frontend`, `web-service`, `microservice`, and `worker`;
- add `worktree-info`, `worktree-doctor`, and `clean-worktree`;
- make Compose, volumes, images, ports, and caches worktree-aware;
- validate generated projects with Docker Compose config checks and targeted runtime checks.

Status:
complete for Docker-first templates.
`frontend`, `web-service`, `microservice`, and `worker` now declare
`worktree-ready` metadata and expose worktree-aware Makefile and Compose workflows.

### Phase D: Native Template Implementation

- update `apple`, `android`, and `harmonyos`;
- isolate native build caches and local output;
- add optional debug identity suffixes where practical;
- validate generated projects with at least lightweight native build or doctor checks.

Status:
complete for native templates.
`apple`, `android`, and `harmonyos` now declare `worktree-ready` metadata and
expose worktree-aware diagnostics, cleanup, native cache paths, local config
visibility, and debug identity suffix hooks.

### Phase E: Release Hardening

- update README, roadmap, template-system docs, release checklist, and verification matrix;
- add a version-specific release-prep document;
- run repo tests and template validation;
- gather fresh generated-project evidence for the templates touched most deeply.

## Non-Goals

The following should stay out of `0.6.0` unless the scope changes:

- building a full Git worktree management CLI inside BiucingCLI;
- automatically creating or deleting Git worktrees;
- adding a daemon, registry, or background coordinator;
- guaranteeing conflict-free use of external shared services the user manually points multiple worktrees at;
- replacing Docker Compose, Gradle, Tuist, hvigor, or existing platform tools;
- supporting migration of old generated projects beyond documentation and optional guidance.

## Exit Criteria

`0.6.0` should be considered ready when:

- every template declares its worktree isolation support in metadata;
- every template exposes worktree diagnostics and cleanup guidance appropriate for its platform;
- Docker-first templates isolate Compose project names, volumes, images, dependency stores, caches, and host ports;
- native templates isolate the main build/cache/signing/app-identity collision points;
- `biucing validate` catches missing worktree contract fields;
- the verification matrix includes explicit parallel-worktree checks;
- docs explain how to run two worktrees side by side without manual cleanup.

## Suggested Changelog Direction

If this scope lands, the `0.6.0` changelog should read as a worktree-first reliability release:

- added a shared worktree isolation contract across all starters;
- made Docker-first starters safe for parallel Compose and cache use;
- improved native starter cache, signing, and debug identity isolation;
- added diagnostics and cleanup commands for worktree-local state;
- expanded validation and release evidence around parallel development workflows.
